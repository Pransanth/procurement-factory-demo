# P1-DEMO-5

Status: VERIFYING

## Befund

`app/services/user_admin_service.py:change_user_role` entscheidet über die Berechtigung zum Ändern
von Benutzerrollen anhand einer Ausschlussprüfung: abgelehnt wird nur, wer die Rolle `member` hat
(`if actor.role == "member": raise ValueError(...)`). Jede andere Rolle passiert die Prüfung. Ein
Benutzer mit der Rolle `approver` — im Datenmodell (`app/db.py`, `users.role CHECK(role IN
('member', 'approver', 'admin'))`) die mittlere, nicht die administrative Rolle — kann damit
Rollen innerhalb seiner Organisation vergeben, einschließlich der Rolle `admin`, und
einschließlich der Vergabe an sich selbst.

Die Organisationsgrenze ist dabei intakt: Akteur und Ziel werden über
`app/repositories/users.py:get_by_id` org-gescoped aufgelöst, ein Benutzer einer fremden
Organisation wird nicht gefunden. Der Befund ist also keine Tenant-Isolation-Verletzung, sondern
eine Rechteausweitung *innerhalb* eines Mandanten: aus `approver` wird `admin`, dauerhaft und
über den regulären Aufrufpfad.

Reproduktion (gegen eine frische In-Memory-DB via `app/db.py:init_db`):

```python
from app.db import init_db
from app.repositories import organizations, users
from app.services import user_admin_service

conn = init_db(":memory:")
org = organizations.create(conn, "Acme Corp")
carol = users.create(conn, org.id, "carol@acme.example", "Carol", "approver")

updated = user_admin_service.change_user_role(conn, org.id, carol.id, carol.id, "admin")
# updated.role == "admin" -- Carol hat sich selbst zum Administrator gemacht.
# Kein Fehler, keine Ablehnung; der Vorgang wird zusaetzlich als
# audit_log-Eintrag "user.role_changed" als regulaere Administration verbucht.
```

Das bestehende Testset zu diesem Modul (`app/services/test_user_admin_service.py`) deckt den Fall
nicht ab: es prüft, dass ein `admin` Rollen vergeben darf, dass ein `member` abgewiesen wird, dass
unbekannte Rollenwerte abgelehnt werden und dass die Organisationsgrenze hält — aber nicht, welche
Rollen zwischen `member` und `admin` die Prüfung passieren, und nicht, was beim Ändern der eigenen
Rolle geschieht.

Dies betrifft einen anderen Codepfad als P1-DEMO-1 (Job-Handler), P1-DEMO-2 (Anlegen einer
Anfrage) und P1-DEMO-3 (Entscheidung über eine Anfrage in
`app/repositories/approvals.py:record_decision`) und ist unabhängig von P1-DEMO-4: hier geht es um
die Benutzerverwaltung (`users`-Tabelle) im Schreibpfad, nicht um Beschaffungsdaten und nicht um
einen Lesepfad.

## Analyse

Root Cause: app/services/user_admin_service.py:change_user_role() authorizes the acting user by exclusion instead of by allowlist: line 31 reads "if actor.role == 'member': raise ValueError(...)", so exactly one role is denied and every other value of the column passes. The data model (app/db.py line 29: role TEXT NOT NULL CHECK(role IN ('member', 'approver', 'admin'))) defines three roles, of which only 'admin' is administrative; 'approver' is the middle role, meant to decide procurement requests (see app/repositories/approvals.py:43, which correctly allowlists "approver, admin" for that separate operation). Because the check names who may not act instead of who may, an 'approver' passes it and can assign any role in ASSIGNABLE_ROLES -- including 'admin', including to themselves, since nothing compares actor_user_id with target_user_id either. The module already contains a correct allowlist one screen above (ASSIGNABLE_ROLES on line 12, checked on line 22), but it constrains the *target role value*, not the *acting user's authority*; the asymmetry between those two checks is the defect.
Affected Components: app/services/user_admin_service.py (change_user_role, the sole authorization point for role administration; it is the only caller of app/repositories/users.py:update_role in production code). Not affected: app/repositories/users.py (update_role is a deliberately unauthenticated, org-scoped writer -- it is the storage layer, not the decision point, and its org scoping is intact and independently tested), app/repositories/approvals.py (already uses the correct allowlist form since P1-DEMO-3; different operation, no overlap), app/db.py (the CHECK constraint is correct and is not the gap -- the gap is that 'approver' is treated as administrative by a service that never asks whether it is), app/services/reporting_service.py (P1-DEMO-4, already closed, different codepath: a read path over procurement data, not the user-administration write path).
Relevant Architecture: This codebase separates storage from authorization: every function under app/repositories/ takes organization_id and enforces tenant isolation per function, but role/permission decisions live in exactly one place per operation -- the service function, or the repository choke point that every caller passes through. P1-DEMO-3 established the shape such a decision is supposed to have: load the actor, then test its role against an explicit allowlist of roles that may perform this operation ("if approver.role not in ('approver', 'admin'): raise"). change_user_role is the same kind of decision for a different operation, but was written as its logical inverse. Nothing in the codebase structurally distinguishes the two forms today: an exclusion test and an allowlist test look equally deliberate in review, which is precisely why the defect survived a test suite that already covers the admin path, the member path, the invalid-role path and the organization boundary -- it simply never asked what the third role does.
Recommended Repair: Replace the exclusion test in change_user_role() with a positive allowlist, expressed as a module-level constant next to the existing ASSIGNABLE_ROLES: ROLE_ADMINISTERING_ROLES = ("admin",), checked as "if actor.role not in ROLE_ADMINISTERING_ROLES: raise ValueError(...)", placed exactly where the current check is (after the actor is resolved, before the target is loaded and before any write). Only 'admin' administers roles; 'approver' loses an authority it was never meant to have. A separate self-change prohibition is deliberately NOT added: with an admin-only allowlist, self-escalation is already impossible (an admin is at the maximum privilege, so changing their own role can only be a demotion), and a blanket self-change ban would remove the only path by which an admin can reduce their own privilege -- unlike P1-DEMO-3's self-approval case, where acting on one's own request is a control-integrity problem regardless of role. The error message keeps naming the actor's actual role, so an operator sees why the call was refused.
Regression Test Plan: A new, dedicated regression file app/services/test_user_admin_role_escalation_regression.py, written and proven red against today's unmodified code: (1) an 'approver' promoting themselves to 'admin' must raise ValueError and must leave their stored role unchanged -- today this succeeds exactly as reproduced in the Befund section; (2) an 'approver' promoting a colleague must raise ValueError and leave the colleague's role unchanged -- today it succeeds, showing the escalation is not limited to self-service; (3) a failed attempt must write no audit_log entry, so a rejected escalation cannot be mistaken for a legitimate administrative act in the record; (4) an 'admin' promoting a member must still succeed after the fix, so the repair cannot be satisfied by simply denying everything. Cases 1-3 must be red before and green after, with unchanged assertions; case 4 is green before and after by design. The existing app/services/test_user_admin_service.py stays untouched and must remain green -- every one of its acting users is an 'admin' or a 'member', so an admin-only allowlist changes none of its outcomes.
Central Guard Plan: A new deterministic AST guard, factory/guards/validate-service-role-authorization.py, wired into the canonical runner factory/guards/run-factory-checks.py as a fifth check over the same --services-dir the P1-DEMO-4 guard already uses (default app/services, test_*.py excluded). It rejects the structural form this finding is made of: any comparison of a role value (an attribute access ".role", or a plain name "role"/"actor_role"/"user_role") against a string literal with == or !=, anywhere in a service module. Such a test decides authority by naming one role; the sanctioned form is a membership test ("in" / "not in") against an explicit allowlist, which is what the repair introduces and what app/repositories/approvals.py already does. The guard therefore does not merely re-check this one function -- it makes the exclusion-style authorization test unwritable in the service layer, which is the class of defect, not just its instance. Own unit tests in factory/guards/test_validate_service_role_authorization.py pin the pre-fix line as a rejected fixture and the post-fix line as an accepted one; cases in factory/guards/test_run_factory_checks.py additionally exercise the new check in GitHub CI, which runs that module and the canonical runner without any change to .github/workflows/factory-ci.yml.
Expected Blast Radius: The runtime change is one condition plus one module-level constant in one function; no schema change, no signature change, no repository change, no change to any other service. Behaviour changes for exactly one input class: an actor whose role is 'approver' now gets ValueError instead of a successful role assignment. No existing test exercises that class (app/services/test_user_admin_service.py uses only 'admin' and 'member' actors), and no other production code calls change_user_role, so nothing else can regress. The new guard is additive, affects no runtime path, and applies to the three current files in app/services/: after the fix none of them contains an equality comparison against a role literal, so it passes on the whole existing service layer.
Risk Assessment: Risk of the fix is low and bounded: additive tightening in a single function, mirroring a pattern already proven in this codebase (P1-DEMO-3), with a clear error path and no data migration. The one behavioural consequence worth stating plainly is intended, not accidental: any workflow that today relies on approvers administering roles stops working -- that is the vulnerability being removed, and the demo application has no such legitimate workflow. The guard's residual risk is a false positive on a future non-authorization comparison against a role literal in a service module, which would surface as a deterministic, precisely-worded failure and can then be reconsidered explicitly rather than silently. Risk of not fixing is a live, reproducible privilege escalation inside a tenant: any 'approver' can make themselves 'admin' through the regular call path, and the act is recorded in the audit log as ordinary administration, so the escalation also degrades the record that would be used to detect it. This is a normal, autonomously decidable technical repair -- no irreversible consequence, no unusual uncertainty.
